# ADR-0012: 邀请制多用户与 Monitor 归属模型

- 状态：Accepted
- 日期：2026-11-05

## 背景

Phase 4A/4B 只有单一管理员账号。邀请制托管试用需要让多个外部用户各自登录、各自管理监控，同时满足：

- 不开放公开注册，避免滥用和不可控增长；
- 不同用户不能互读、互改、互删业务数据；
- 管理员保留账号运维能力，但默认不能读取用户业务内容；
- 现有单管理员数据可平滑迁移，不丢失历史。

## 决策

1. 保持模块化单体与单库；以 `monitor.user_id` 作为所有业务数据的归属根。
2. `app_user` 增加 `role`（`ADMIN`/`USER`）与 `status`（`ACTIVE`/`DISABLED`）；注册只能创建 `USER`。
3. 注册采用邀请码：
   - 只存 SHA-256 摘要，明文仅创建响应返回一次；
   - 名额通过条件 UPDATE 原子占用，并发注册不超卖；
   - 支持备注、最大使用数（1–100）与过期时间；撤销写入 `revoked_at`。
4. 业务 API 从会话解析当前用户，所有 Monitor、CheckResult、Incident、心跳凭证与通知投递查询都带归属条件；跨用户访问统一按 404 处理，避免泄露存在性。
5. `ADMIN` 控制台只返回账号元数据与监控数量，不返回其他用户的 Monitor 名称、目标 URL、历史或通知内容。
6. 账号状态：
   - `DISABLED` 不能登录，已有会话立即失效；
   - 禁用后调度跳过该账号，重新启用恢复；
   - 不能禁用最后一个启用 `ADMIN`；并发禁用通过锁定启用管理员行保证至少保留一个。
7. 迁移顺序为可空列回填 → 业务隔离 → `NOT NULL` 收口（V15/V16），回退策略为恢复迁移前备份。
8. 邀请码创建/撤销、账号状态变更与重置码生成写结构化审计日志，不记录明文凭据。

## 备选方案

- **共享管理员账号**：实现最省，但无归属、无隔离，无法满足试用与审计。
- **组织/团队与细粒度 RBAC**：当前目标用户是单人或小团队，复杂度与运维成本过高。
- **每用户独立数据库/Schema**：隔离更强，但迁移、备份与连接池复杂度不适合单 VPS。
- **公开注册**：与邀请制试用假设冲突，且需要邮件/人机校验等额外边界。

## 后果

- 无公开注册；管理员承担发码与账号处置责任，需要控制台与审计。
- 所有业务查询必须显式带归属条件；新增实体必须从 Monitor 推导归属并补跨用户测试。
- 备份包含全部用户数据；恢复后会话与通知渠道密钥需同时可用。
- 管理员默认不能查看业务内容，排障需用户提供信息；后续如需要“代维模式”，必须新增 ADR 与授权流程。
- 1–3 人的小团队共享可见性尚未实现；当前模型是“每人独立数据”。
