# ADR-0013: 用户级通知渠道与凭据加密

- 状态：Accepted
- 日期：2026-11-05

## 背景

单管理员阶段只支持全局 Telegram，凭据来自环境变量。邀请制试用面向国内微信用户，需要：

- 每个用户配置自己的 PushPlus、息知或邮件接收方式；
- 用户凭据属于敏感数据，不能明文落库或出现在日志/API/UI；
- 单一渠道失败不能阻断其他渠道；
- 通知投递可追踪、可重试、可限频，避免刷爆第三方额度；
- 现有 Telegram 行为与数据兼容。

## 决策

1. 新增 `notification_channel`：
   - `user_id` 归属、`type`（`PUSHPLUS`/`XIZHI`/`EMAIL`）、唯一名称、启用状态；
   - 凭据 JSON 使用 **AES-256-GCM** 加密，随机 12 字节 IV，密文 Base64 存 `config_ciphertext`；
   - 密钥来自 `BEATWARD_CHANNEL_SECRET_KEY`（Base64 32 字节）；有渠道数据而密钥缺失时拒绝启动。
2. API/UI 只返回掩码；完整凭据只在写入请求中出现一次，不进入响应、日志或通知内容。
3. 通道选择：
   - PushPlus 与息知使用内置官方端点，不接受用户上传 URL；
   - 邮件使用管理员配置的全局 SMTP，用户只提供收件邮箱；
   - 旧 Telegram 仅作为无用户渠道时 `ADMIN` 的 legacy 通道，保留既有环境变量行为。
4. `notification_delivery` 增加可空 `notification_channel_id`：
   - 新投递按 `(incident_id, event_type, notification_channel_id)` 唯一；
   - 历史 Telegram 行按 `(incident_id, event_type, channel)` 唯一；
   - 渠道删除使用 `ON DELETE SET NULL`，调度遇到空渠道或禁用渠道标记失败并跳过。
5. 入队时展开用户所有启用渠道；每渠道独立发送、独立重试；单渠道失败不影响其他渠道。
6. 限频：每用户每渠道 10 条/分钟、50 条/小时，超限标记 `FAILED` 并记录 WARN；测试发送共用额度。
7. 每用户最多 3 个启用渠道；写入时锁定 `app_user` 行后计数，避免并发超配。

## 备选方案

- **明文或哈希存凭据**：PushPlus/Xizhi 需要原始 token/key，哈希不可用；明文违反安全基线。
- **用数据库内密钥列加密**：密钥与密文同库，备份泄露即失效；无法离线分离。
- **只提供全局渠道**：无法满足用户各自接收与多用户隔离。
- **允许用户自定义 webhook URL**：SSRF 与任意外联风险高，当前非目标。
- **每用户无限渠道**：第三方额度与运维复杂度不可控。

## 后果

- 密钥必须离线备份；丢失后所有渠道需重新绑定。
- 应用启动增加密钥与渠道数据的联合校验；密钥轮换需要单独迁移方案（当前未提供）。
- 第三方端点与 SMTP 成为外部依赖；限频是内存态软限制，重启后清空。
- 息知协议把 Key 放在 URL 路径；必须禁止记录请求 URL 与开启客户端调试日志。
- 新增 IM 渠道需补 sender、配置校验、规范与测试，不改变本 ADR 的加密与投递骨架。
