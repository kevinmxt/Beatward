# Beatward Phase 4C 路线图审阅建议

## 结论

Phase 4C 已具备进入 Phase 4D 的条件。路线图的阶段顺序合理：4C 完成邀请制多用户与用户级通知，4D 做上线前成本、备份、审计和账号处置收尾，5B 再进行真实 VPS 公网验收，Phase 6 验证试用留存与产品价值。

## 建议调整/补充

### 1. 将限频器容量边界纳入 4D

当前 `NotificationRateLimiter` 的 `MAX_KEYS` 并非严格上限。建议在 4D 增加有界键管理与容量测试，保持内存成本可预测。不要为了修复而引入 Redis；当前单实例阶段用进程内有界结构即可。

### 2. 明确账号禁用语义

当前实现能阻止禁用账号被后续调度扫描，但正在执行的 Probe/Heartbeat/通知可能与禁用操作并发。建议在 4D 文档中明确“禁用后不再启动新任务，已开始任务允许完成一次”或实施更严格的互斥协议，并据此编写并发验收。

### 3. 4D 审计清单要落到事件级验收

至少覆盖邀请码创建/撤销、用户禁用/启用、重置码生成、通知渠道创建/更新/启停/删除、登录失败/限流。统一结构化字段并确保凭据脱敏。无需引入独立审计数据库或复杂审计 UI。

### 4. 继续坚持单机低成本架构

现有用户行锁、PostgreSQL、单实例调度和事务 outbox 对 3–5 人邀请试用是合理的。暂时不需要 Redis、Kafka、Kubernetes、微服务拆分或复杂组织 RBAC。先用 4D 容量基线验证 2C4G 目标规格。

## 建议的 4D 顺序

1. 限频器有界化与后台禁用竞态语义确认。
2. 多用户备份/恢复复验，包含 `BEATWARD_CHANNEL_SECRET_KEY` 离线备份与恢复后解密验证。
3. 审计事件补齐及脱敏测试。
4. 账号禁用/删除的数据保留和手工处置流程。
5. 5 用户 / 100 Monitor / 60 秒 / 30 天容量与费用测算。
6. 形成 Phase 4D 验收证据，再进入 Phase 5B。

## 不建议提前做

- 公开注册、支付计费、订阅管理。
- 多组织/团队/复杂 RBAC。
- Redis、消息队列和多实例调度。
- 多区域探测、Kubernetes、APM。

这些功能都不属于当前邀请制试用的上线硬门槛。
