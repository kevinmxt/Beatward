# 安全规范

安全要求是 MVP 的必需条件。

## SSRF 与目标 URL
用户可配置目标 URL，因此所有探测目标均视为不可信输入。

必须：
- 只允许 HTTP/HTTPS。
- 只允许全球可路由的公共 IP 地址；拒绝其他所有地址。
- 对解析后的 IP 执行校验。
- 考虑 DNS 重绑定风险。
- 对重定向执行严格限制；禁止未经校验跳转到受限地址。
- 设置连接、响应和响应体大小限制。
- 创建时和每次执行时都进行必要校验。

不能可靠防护时，缩小允许访问范围；不能只在创建时检查 URL 一次。

### 地址分类策略

策略依据 IANA IPv4/IPv6 Special-Purpose Address Registries（查询日期 2026-10-22）维护显式受限前缀清单，而不是依赖零散的 `InetAddress` 分类方法：

- IPv4 受限前缀：`0.0.0.0/8`、`10.0.0.0/8`、`100.64.0.0/10`、`127.0.0.0/8`、`169.254.0.0/16`、`172.16.0.0/12`、`192.0.0.0/24`、`192.0.2.0/24`、`192.88.99.0/24`、`192.168.0.0/16`、`198.18.0.0/15`、`198.51.100.0/24`、`203.0.113.0/24`、`224.0.0.0/4`、`240.0.0.0/4`。
- IPv6 默认拒绝 `2000::/3` 之外的地址；在 `2000::/3` 内额外拒绝 `2001::/32`（Teredo）、`2002::/16`（6to4）、`2001:1::1/128`、`2001:1::2/128`、`2001:2::/48`、`2001:10::/28`、`2001:20::/28`、`2001:30::/28`、`2001:db8::/32`、`3fff::/20`。Teredo/6to4 可封装 IPv4，因此采取保守的整段拒绝；部分协议 anycast 地址也一并拒绝。
- IPv4-mapped IPv6（`::ffff:0:0/96`）和 NAT64（`64:ff9b::/96`）提取内嵌 IPv4 后复用 IPv4 判定；内嵌受限地址时整个解析结果被拒绝。已废弃的 IPv4-compatible IPv6（`::/96`）直接拒绝。`64:ff9b:1::/48` 等其他非全球单播前缀由默认拒绝规则处理。
- 一次 DNS 返回多个地址时，任一地址受限即拒绝该组结果。
- 继续禁止自动重定向，3xx 作为普通响应按预期状态码判定。

应用层校验不能替代网络隔离。部署时必须同时配置出站防火墙或等价策略，限制应用可访问的目标范围。

## 认证与授权
- 公网管理入口的发布门槛见 [`../quality/deployment.md`](../quality/deployment.md) 的“公网发布硬性门槛”；本节规定认证实现要求。
- 认证实现、会话、CSRF、登录限流与启动校验见 [`../specs/auth.md`](../specs/auth.md)；决策背景见 [ADR-0008](../adr/0008-admin-auth-session.md)。
- 账号存于 `app_user`，首次启动由引导变量创建唯一管理员；空表缺少引导变量、用户名或哈希非法、非回环监听且未启用 Secure Cookie 时拒绝启动。
- 账号角色为 `ADMIN`/`USER`，状态为 `ACTIVE`/`DISABLED`；禁用账号不能登录，管理员禁用会立即失效该用户全部会话，未主动失效的旧会话也会在下一次请求时被拒绝。
- 管理员控制台仅允许 `ADMIN` 访问；邀请码撤销、账号启用/禁用与重置码生成写入结构化审计日志（`dev.beatward.audit`），只记录 actor/对象 ID、状态与结果，不记录明文码。
- 用户通知渠道凭据使用 AES-256-GCM 加密存储，密钥来自 `BEATWARD_CHANNEL_SECRET_KEY`（Base64 32 字节）；存在渠道数据而密钥缺失时拒绝启动。API、UI、日志、错误响应与通知内容只使用掩码或占位，不返回完整凭据。
- PushPlus 与息知只访问内置官方端点，不接受用户自定义 URL；`beatward.notification.endpoints.*` 覆盖仅供测试或受控代理使用，不对用户开放。邮件使用管理员配置的全局 SMTP。所有外发请求必须设置连接与响应超时。
- 通知投递按 `(incident_id, event_type, notification_channel_id)` 唯一；每用户每渠道 10 条/分钟、50 条/小时，超限标记失败并记录 WARN，不阻塞其他渠道。
- 密码使用成熟的安全哈希算法。
- 邀请码与一次性密码重置码使用高熵随机值，数据库只保存 SHA-256 摘要，明文只在创建响应中返回一次；注册与重置分别按客户端地址和摘要限流，且使用独立于登录的限流键空间。
- 正确配置 Cookie / Session 安全属性。
- 根据认证方式实施 CSRF 防护。
- 对登录失败进行限制。
- 对受保护接口进行未授权访问测试。
- 所有管理操作都要检查权限。

## 密钥与敏感信息
- 不将真实密钥、密码、Bot Token 或私钥提交到 Git。
- 使用环境变量或安全部署配置注入密钥。
- `.env.example` 只允许占位值。
- 不记录完整心跳令牌、密码和敏感请求头。
- 不记录完整邀请码、重置码或渠道凭据；管理员操作日志只记录对象 ID 与结果。
- 心跳令牌只以 SHA-256 摘要持久化；上报接口不记录完整令牌或请求 URI。
- 心跳上报的限流、请求体上限与 HTTPS 强制要求见 [`../specs/heartbeat.md`](../specs/heartbeat.md#上报接口)；可信代理与客户端地址规则统一见 [`../specs/auth.md`](../specs/auth.md#可信代理与客户端地址)。
- 默认不记录被监控 API 的完整响应正文。
- 错误摘要必须截断并避免敏感信息。
- 不向用户返回内部堆栈、连接串或环境变量。

## 网络和部署
- PostgreSQL 不直接暴露到公网。
- 生产环境使用 HTTPS。
- 关闭无必要的公网端口。
- SSH 优先使用密钥认证。
- 使用权限受限的数据库账号。
- 保护备份文件和日志。
- 管理 API、心跳凭证和公开状态页必须具有清晰的权限边界。

## 安全测试最低范围
- 非法 URL 和协议
- localhost / 私有 IP / 链路本地地址
- 重定向到禁止地址
- 无效或撤销的心跳令牌
- 未认证访问管理接口
- 敏感信息日志检查
- 超长输入和非法配置
